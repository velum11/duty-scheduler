# 개발 계획서 (development-plan.md)

## 1. 개발 원칙

- Phase 단위로 **항상 동작하는 상태**를 유지하며 점진 개발한다.
- 핵심 가치(스프레드시트 방식 근무표 등록 + 모바일 조회)를 우선 완성한다.
- **초기 Phase는 Supabase 없이도 실행 가능**해야 한다 — `data/sample/` 샘플 데이터 로컬 폴백으로
  화면과 로직을 먼저 완성하고, Supabase 실연동은 데이터 계층(modules/db.py) 교체로 수행한다.
- 각 Phase 종료 시 체크리스트로 수동 검증한다.
- 자동 근무표 생성 기능은 다루지 않는다. MCP는 사용하지 않는다.

## 2. Phase 계획

### Phase 1 — 기반 구축 (프로젝트 셋업 + 인증)

**산출물**
- `requirements.txt` (streamlit, supabase, pandas, streamlit-cookies-controller)
- `.streamlit/config.toml` (업무용 테마), `.streamlit/secrets.toml` (템플릿 + .gitignore)
- `modules/db.py` — 데이터 접근 계층: Supabase 클라이언트 + **secrets 미설정 시 샘플 데이터 폴백**
- `data/sample/` — 부서/조/사용자/근무형태/근무표 샘플 데이터
  (근무형태는 실제 근무표 샘플 기준 10종: 주·야·OFF·연차·특주·특야·야-4·야-6·출산휴가·자녀결혼)
- `modules/auth.py` — 사번 로그인, 세션 토큰 발급/검증, 쿠키 저장/복원, 로그아웃
- `app.py` — 로그인 게이트 + role(USER/MANAGER/ADMIN)별 메뉴 라우팅 뼈대
- `modules/ui.py` — 공통 헤더/필터 카드/뱃지 초안

**완료 기준**
- [ ] Supabase 설정 없이 샘플 데이터로 앱 실행
- [ ] 사번으로 로그인/로그아웃 가능
- [ ] 새로고침·브라우저 재시작 후에도 로그인 유지 (쿠키 토큰)
- [ ] 미등록/퇴사 사번 거부
- [ ] USER/MANAGER/ADMIN별로 다른 메뉴 표시

**산출물**

- 저장 검증: 코드/사번 중복 차단, 미등록 참조 차단, 사용 중 데이터 삭제 경고

**완료 기준**

- [ ] 사번/부서코드/조코드/근무형태코드 중복 저장 차단
- [ ] 사용자 등록 시 부서/조/권한을 기준정보 selectbox로 선택

### Phase 3 — 근무표 등록/수정 + 전체 조회 (핵심)

**산출물**
- `modules/schedule.py` — **가로형 그리드 ↔ 세로형 레코드 변환**(pivot/melt), 정규화(trim/대문자/전각),
  저장 전 검증(database.md §6.2: 사번 존재 → 성명 매칭 폴백 → 부서/조/근무코드 대조 → 중복 검출),
  diff 산출(신규/변경/**삭제 후보 분리**), 월 단위 upsert, **명시적 확인을 거친 삭제만 반영**, 배치/변경 이력 기록
- 근무표 등록/수정 화면 — 년/월/부서/조 선택, 표준 입력 컬럼(사번·성명·부서·조/팀·날짜별 근무코드) 그리드,
  [조회]/[저장], **저장 전 미리보기(신규/변경 건수 + 삭제 후보 목록·[삭제 반영] 선택)**
- 전체 근무표 조회 화면 — 필터(월/부서/조/직원/근무형태), 색상 그리드(읽기 전용), 사용자별 집계
- MANAGER 편집 범위 제한 (소속 부서만)

**완료 기준**
- [ ] 년/월/부서 선택 → 저장된 근무표 로드 (없으면 재직자 빈 그리드)
- [ ] 실제 엑셀 근무표(가로형) 범위 복사 → 그리드 붙여넣기 정상 동작
- [ ] 저장 시 가로형 → 세로형 `work_schedules` 변환 정확 (재조회 pivot 결과 일치)
- [ ] 행 추가/삭제 후 저장 정상 반영
- [ ] 검증 7종 동작: 미등록 사번/성명 불일치/성명 매칭 실패/미등록 부서/미등록 조/미등록 근무코드/사번+일자 중복 — 각각 위치를 알려주며 저장 차단
- [ ] 사번이 빈 행이 성명 유일 매칭으로 저장되는지 확인
- [ ] 저장 전 미리보기(신규/변경 건수 + 삭제 후보 목록) 표시
- [ ] **빈 셀이 있어도 기존 근무가 자동 삭제되지 않음** — [삭제 반영] 선택 시에만 삭제
- [ ] 저장 → 재조회 시 데이터 일치
- [ ] 저장 시 `schedule_import_batches` 1건 + 달라진 셀만 `schedule_change_logs` 기록 (확정 삭제는 DELETE 로그)

## 3. 기술 리스크와 대응

| 리스크 | 내용 | 대응 |
|--------|------|------|
| 로그인 유지 | Streamlit은 새로고침 시 session_state 초기화 | 쿠키 컴포넌트 + login_sessions 토큰 검증으로 복원. Phase 1에서 가장 먼저 검증 |
| data_editor 열 수 | 31개 날짜 열 + 고정 열에서 편집 성능 | 월 단위로만 로드, 부서/조 필터로 행 수 제한. 문제 시 반월 분할 표시 검토 |
| 붙여넣기 형식 | 엑셀 데이터에 공백/소문자/전각 문자 혼입 | 저장 전 정규화(trim, 영문 대문자, 전각 변환) 후 검증 |
| 빈 셀 오삭제 | 붙여넣기 데이터의 빈칸(미작성 날짜 등)으로 기존 근무가 지워질 위험 | **빈 셀 자동 삭제 금지** — 삭제 후보를 별도 목록으로 보여주고 명시적 [삭제 반영] 선택 시에만 삭제 (database.md §6.4) |
| 성명 매칭 오류 | 사번 없는 행의 성명 매칭 시 동명이인 | 유일 매칭 실패 시 오류 처리 + 사번 입력 유도 |
| 동시 편집 | 두 관리자가 같은 월을 동시에 저장 | 소규모 조직 전제로 후저장 우선(last-write-wins). 배치 이력으로 추적 가능, 저장 시각 표시로 완화 |
| 모바일 UX | Streamlit 기본 UI가 모바일에 넓음 | 직원 화면은 카드/리스트형으로 별도 구성, 최소 CSS 적용 |
| 사번 단독 로그인 | 타인 사번 도용 로그인 가능 | MVP 수용 리스크로 문서화. 향후 사번+이름/PIN 강화 (아래 확장 후보) |
| 폴백↔실DB 차이 | 샘플 모드와 Supabase 동작 차이 | db.py 인터페이스를 동일하게 유지, Phase 5에서 전 시나리오 재검증 |

## 4. 향후 확장 후보 (이번 범위 제외)

- 로그인 보안 강화: 사번+이름 확인 → 사번+PIN → 실제 인증(이메일/SSO)
- 근무표 자동 배정(제약 조건 기반) — **명시 요청 시에만 착수**
- 근무 교환 신청/승인 워크플로
- 알림 (이메일/카카오톡)
- 변경 이력 조회 화면 (관리자용 감사 뷰)
- 근태/급여 시스템 연계
