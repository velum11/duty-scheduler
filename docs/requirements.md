# 기능 요구사항

이 문서는 제품이 제공해야 하는 기능과 데이터 계약의 기준입니다. 색상, 패널 수, 화면 방향, 트리 여부 같은 구체적인 시각 표현은 정의하지 않습니다.

## 1. 제품 목적

생산 현장의 월별 근무표를 편성·조회하고, 직원이 본인 근무를 확인할 수 있게 합니다. 자동 근무표 생성이나 최적화는 현재 제품 범위가 아닙니다.

## 2. 사용자와 권한

권한값은 `ADMIN`, `MANAGER`, `USER` 세 가지입니다.

### ADMIN

- 전체 근무표 편성·조회
- 본인 근무표 조회
- 사용자, 조직, 근무형태 기준정보 관리

### MANAGER

- 담당 부서 범위의 근무표 편성·조회
- 본인 근무표 조회
- 기준정보 변경 불가

### USER

- 개인 대시보드
- 허용된 월간 근무표 조회
- 본인 근무표 조회
- 편성 및 기준정보 변경 불가

서버 측 route 진입에서도 권한을 다시 확인해야 합니다. 메뉴를 숨기는 것만으로 접근 제어를 대신하지 않습니다.

### 업무별 담당 권한 (2026-08-07 도입)

계층 role 3종과 별개로, 업무별 담당(예: 숙소관리 담당, 업무요청 담당)은 **직교하는 담당 권한(capability)** 으로 부여합니다. role 은 3종 그대로 유지되며 담당은 role 을 바꾸지 않습니다(안전담당자가 USER 인 것과 같은 원칙).

- 담당 부여·회수는 사용자 관리 화면(ADMIN 전용)에서 하며, 담당 종류의 신설은 스키마 변경 없이 앱 코드 등록으로 확장합니다.
- 담당자는 **알림 수신 이메일**을 여러 개 가질 수 있고, 주소마다 수신 범위(전체 또는 특정 담당 업무)를 지정합니다 — 같은 사람이 업무 A는 1개, 업무 B는 2개 주소로 받을 수 있습니다. 이메일은 저장 시 소문자로 정규화하고, 같은 사람·같은 범위의 대소문자만 다른 중복을 저장하지 않습니다.
- 업무 알림의 수신자 = 그 업무 담당 권한 보유자들의 이메일 중 범위가 '전체' 또는 해당 업무인 주소. 담당자는 있는데 주소가 없으면 발송 계층이 이를 침묵시키지 않고 대비책(기본 수신처 또는 관리 화면 경고)을 가져야 합니다.
- 담당 권한 판정도 role 과 동일하게 서버 측에서 재확인합니다.

## 3. 로그인

- 사용자는 사번으로 로그인합니다.
- 입력 앞뒤 공백을 제거하고 영문 대소문자를 무시해 조회합니다.
- 비교를 위한 정규화가 DB의 사번 원본을 변경해서는 안 됩니다.
- 같은 사번이 대소문자만 다르게 중복되면 활성 사용자를 우선하고, 그 안에서는 정확히 일치하는 값을 우선합니다.
- 비활성 사용자는 로그인할 수 없습니다.
- 퇴사일이 지난 사용자는 로그인할 수 없고, 발급된 토큰을 폐기해 다음 세션 검증(새 탭·새로고침·재접속)부터 차단합니다. 이미 열려 있는 화면 세션은 즉시 종료를 보장하지 않습니다(권한·재직 변경의 세션 반영은 앱 전역에서 같은 방식 — 재로그인 시 확정). 퇴사일 당일까지는 재직으로 봅니다. 미등록 사번·오답 비밀번호·퇴사 계정은 같은 문구로 거절합니다(사용자 열거 방지). — 2026-08-07 제품 결정
- 로그인 세션은 서버가 발급한 토큰으로 유지하며 로그아웃 시 폐기합니다.

인증은 비밀번호 방식입니다(2026-08-05 도입): 초기 비밀번호는 사번과 같고 최초 로그인 시 변경을 강제하며, 초기 비밀번호에는 유효기간을 둡니다. 연속 실패 시 일시 잠금하고, 분실 시 ADMIN이 사번으로 재초기화합니다. 세부 파라미터(세션 TTL·잠금 횟수 등)는 `modules/config.py`가 소유합니다. 외부 공개 수준의 보안이 필요하면 Supabase Auth 등 별도 인증 체계를 설계해야 합니다.

## 4. 데이터 모드

- `sample`과 `supabase` 중 하나를 명시적으로 선택합니다.
- 설정 누락, 연결 오류, repository 오류를 sample 데이터로 자동 대체하지 않습니다.
- sample 모드의 쓰기는 현재 Streamlit 세션 안에서만 유지될 수 있습니다.
- Supabase service role key는 서버에서만 사용합니다.

## 5. 근무표

### 월별 편성

- 연월, 부서, 조 기준으로 근무표를 조회·편집합니다.
- 직원 행과 일자 열을 사용해 근무형태를 입력할 수 있습니다.
- **조(근무조)는 기준정보가 아니라 편성표에서 직접 입력하는 자유 텍스트입니다** — 2026-08-07 제품 결정(A/B/C조를 운영단위 기준정보에서 제외). 한 글자 입력(`A`)은 `A조`로 자동 보정하되, 두 글자 이상 입력은 그대로 둡니다. 기준정보 대조로 저장을 차단하지 않습니다.
- 저장 전 직원, 부서, 근무형태, 날짜를 검증합니다.
- 직원 한 명의 같은 날짜에는 근무 한 건만 존재합니다.
- 저장된 행만 조회하며, 데이터가 없는 월에 전체 직원을 자동으로 저장하거나 편성하지 않습니다.
- 신규 직원 행은 명시적인 행 추가 또는 붙여넣기로 만듭니다.
- 퇴사일이 지난 직원은 편성 명단에서 제외합니다(과거 월의 저장된 기록 조회는 유지).

### 월별 편성 스냅샷

- 직원 한 명과 월 하나에 편성 스냅샷 한 건만 존재합니다.
- 스냅샷은 해당 월의 부서와 조(근무조 텍스트)를 보존합니다. 레거시 운영단위(team) 스냅샷 값은 보존하며, 조 표시가 비어 있으면 레거시 운영단위명으로 폴백합니다.
- 근무 행을 저장할 때 해당 월의 편성이 있으면 연결합니다.
- 편성이 없는 과거 근무는 자동 백필하지 않습니다.
- 편성이 없는 월에서 사용자 현재 소속을 표시용으로 사용할 수 있지만 이를 자동 저장하지 않습니다.
- 편성과 근무 저장 중 일부만 성공하면 성공으로 위장하지 않고 정확한 상태를 알립니다.

### 조회

- 월간 근무표는 연월과 접근 가능한 조직 범위로 조회합니다.
- 비활성(퇴직) 직원의 과거 근무는 해당 월에 기록이 있으면 조회에 표시하고, 퇴직 상태를 라벨 등 색상 외 신호로 구분합니다. 기록이 없는 월에는 표시하지 않습니다(빈 행 금지). — 2026-07-25 제품 결정
- 개인 근무표는 본인 데이터만 조회합니다.
- 근무형태의 약칭과 색상은 기준정보를 사용합니다.
- 정상적인 빈 월과 repository 오류를 구분합니다.

## 6. 기준정보

사용자·조직·근무형태 관리는 같은 편집 모델을 공유합니다. 화면별 도메인 규칙(자연키·검증·삭제 정책)은 각 화면이 소유하고, 공통 편집·상태·저장 계약은 공통 기반에서 제공합니다.

### 공통 편집

- 표에서 직접 편집하고 [저장]으로 일괄 반영합니다. 자동 저장은 없습니다.
- 신규 행은 명시적 행 추가 또는 붙여넣기로만 만듭니다. 자동 빈 행을 추가하지 않습니다.
- 저장은 신규·변경 행이 있을 때만 가능하고, 삭제는 선택된 행이 있을 때만 가능합니다.
- 저장 실패 시 편집 내용(draft)을 유지하고 성공으로 위장하지 않습니다. 검증 실패는 DB 요청 전에 차단하고 해당 행·셀을 표시합니다.
- **부분 성공 처리**: 한 저장 명령이 키 단위로 일부만 성공하면 성공 키와 실패 키를 명시하고, 성공 키만 반영하며 실패 키는 편집 상태로 남겨 재시도할 수 있게 합니다. 성공/실패를 알 수 없는 통신 오류는 전체 성공으로 추정하지 않고 `재조회 필요` 상태로 분리합니다.
- **삭제는 저장과 분리된 명령**입니다. 2단계 확인을 거치며, 삭제 실패는 저장 결과와 섞지 않고 그 자체로 알립니다. 처리 방식은 화면별 삭제 정책을 따릅니다.
- 조직 스키마 capability(조직 그룹 SoT `organization_groups` + 부서 `group_id` 귀속) 준비 상태는 `준비됨 / 미적용 / 확인 실패` 세 가지로 구분합니다. 미적용·확인 실패 상태에서는 **조직 데이터를 쓰는 화면의** 쓰기 동작(추가·편집·삭제·저장)을 UI와 repository 양쪽에서 차단하고 조회만 허용합니다. 조직 데이터와 무관한 화면에는 이 readiness를 요구하지 않습니다. 사용자 안내 문구는 migration 번호 없이 안정 표현("조직 스키마가 준비되지 않아…")을 사용합니다. 도입 이력과 적용 절차는 `docs/database.md`가 소유합니다.

### 사용자 관리

- 사번, 성명, 부서, 직급, 권한, 입사일, 퇴사일, 표시순서, 재직 여부를 관리합니다. — 2026-08-07: 운영단위(조) 편집 칼럼 제거, 입사일·퇴사일 추가
- 사번은 고유해야 합니다.
- 기존 운영단위 배정 값은 화면에서 편집하지 않되 저장 시 지워지지 않게 보존합니다.
- 입사일·퇴사일은 선택 입력이며, 퇴사일은 입사일보다 앞설 수 없습니다. 해석 불가한 날짜 입력은 저장 전에 차단합니다.
- 퇴사일이 지난 사용자는 로그인이 차단되고 편성·현황 명단에서 숨겨집니다. 계정과 과거 기록은 삭제하지 않으며, 퇴사일을 지우면 즉시 복귀합니다. 판정 불가(날짜 해석 실패)는 재직으로 간주합니다 — 잘못 읽은 날짜로 재직자를 잠그는 것이 더 나쁜 오작동이기 때문입니다.
- 비활성화해도 과거 근무와 편성 참조는 유지합니다.
- 조직 확장 스키마가 준비되지 않았을 때 표시순서를 입력하면 전체 저장을 차단합니다. 재직기간 스키마(입사일·퇴사일)가 준비되지 않았을 때 해당 값을 입력하면 같은 방식으로 저장을 차단합니다.

### 조직 관리

2026-08-07 제품 결정: 화면은 **부서 단일 시트**이며, 조직 계층은 부서의 **대분류·중분류 자유 텍스트 2단**으로 사람이 직접 입력합니다. 그룹·운영단위 시트는 화면에서 폐지되었습니다.

- 부서의 코드, 코드명, 대분류, 중분류, 순서, 비고, 사용 여부를 관리합니다.
- 부서 코드는 전역에서 고유합니다.
- 중분류는 대분류 없이 가질 수 없습니다(중간층만 있는 계층 금지). 대분류·중분류는 기준정보 FK가 아닌 자유 텍스트이므로 표기 흔들림은 운영 책임입니다.
- 참조 중인 부서를 무조건 물리 삭제하지 않으며, 참조가 있으면 비활성화를 우선합니다. `ADMIN` 부서는 보호합니다.
- 데이터 모델의 `organization_groups`·`departments.group_id`·`teams`는 보존됩니다(휴면 — 화면 편집 경로 없음). 부서 저장은 기존 그룹 귀속과 운영단위 배정을 변경하거나 지우지 않습니다. 되돌림(그룹/운영단위 화면 복원)이 필요해지면 이 보존 데이터가 출발점입니다.
- 레거시 부서 관리와 조 관리 route는 통합 조직 관리 기능으로 위임할 수 있습니다.

조직 데이터의 계층 관계는 기능 계약입니다. 실제 화면 표현은 사용자 요구와 `DESIGN.md`(§0 화면 유형 규약 포함)를 따르며, 이 문서는 기능 계약만 정의합니다.

### 근무형태 관리

- 코드, 명칭, 분류, 약칭, 시작·종료 시각, 색상, 근무 여부, 수당 영향, 설명, 표시순서, 사용 여부를 관리합니다.
- 코드는 고유해야 하고 기존 근무표가 참조할 수 있으므로 삭제 전 참조를 확인합니다.
- 색상은 유효한 표시값으로 검증합니다.

## 7. 데이터 무결성

- 자연키 공백을 제거하고 필수값을 검증합니다.
- 저장 시 화면에 보이는 일부 행만이 아니라 저장 후 전체 예상 데이터에서 중복과 참조를 검사합니다.
- 사용자 입력 오류는 DB 요청 전에 차단합니다.
- DB 제약 오류를 숨기지 않고 사용자가 이해할 수 있는 메시지로 전달합니다.
- 변경된 행만 upsert하며 조회만으로 데이터를 쓰지 않습니다.
- 소프트 삭제(비활성화)는 과거 근무·편성 참조를 보존합니다. 사용자는 항상 소프트 삭제하고, 참조가 있는 기준정보는 물리 삭제 대신 비활성화합니다. 이 소프트 삭제 계약은 불변입니다.
- 개인정보와 인증정보를 로그, 문서, 브라우저 코드에 노출하지 않습니다.

## 8. 비기능 요구사항

- ADMIN/MANAGER 업무 화면은 1366×768에서 핵심 작업이 가능해야 합니다.
- USER 화면은 모바일 폭에서도 조회와 월 이동이 가능해야 합니다.
- Supabase 오류가 다른 데이터로 위장되지 않아야 합니다.
- 로컬 계약 테스트는 실DB 없이 실행할 수 있어야 합니다.
- 원격 쓰기 테스트는 전용 테스트 프로젝트와 명시적 보호 플래그를 요구해야 합니다.
- 관련 없는 기능과 미커밋 변경을 보존해야 합니다.

- 급여·수당 정산
