# 요구사항 정의서

## 1. 프로젝트 목적

교대 근무 조직의 근무표를 엑셀 대신 웹에서 관리한다.

- 관리자는 익숙한 **스프레드시트 방식 그대로** 수기 입력과 엑셀 복사/붙여넣기로 근무표를 작성·수정한다.
- 직원은 언제든 **모바일 웹으로 본인의 근무**를 확인한다.
- 데이터는 Supabase PostgreSQL에 저장하고, 근무표 변경은 이력으로 남긴다.

이 시스템은 **자동 근무표 생성 또는 자동 배정 시스템이 아니다.**  
근무표 작성 자체는 사람이 하고, 시스템은 입력·검증·저장·조회·이력을 담당한다.

---

## 2. 사용자 정의

| 역할 | 코드 | 설명 | 주 사용 환경 |
|---|---|---|---|
| 직원 | `USER` | 일반 근무자. 본인 근무표만 조회 | 모바일 웹 |
| 매니저 | `MANAGER` | 조장/반장 등. 소속 부서·조의 근무표 조회·편집 | PC 웹 |
| 관리자 | `ADMIN` | 시스템 관리자. 모든 기준정보와 전체 근무표 관리 | PC 웹 |

## 3. 기능 요구사항

| AUTH-03 | 로그인 상태를 유지한다. 새로고침·브라우저 재시작 후에도 재로그인하지 않도록 쿠키 세션 토큰을 사용한다. | 필수 |

### 보안 한계

사번 단독 로그인은 타인의 사번을 아는 사람이 해당 사용자로 로그인할 수 있는 구조다.

초기 사내 사용 범위에서는 이 한계를 인지하고 수용한다.  
향후 다음 순서로 보완할 수 있다.

```text
사번 + 이름 확인
사번 + PIN
정식 인증 방식
```

### 3.2 기준정보 관리

관리자는 다음 기준정보를 관리한다.

```text
사용자
부서
조/팀
근무형태
```

모든 기준정보 등록 화면은 공통 패턴을 따른다.

```text
조회
스프레드시트 편집
수기 입력
엑셀 복사/붙여넣기
행 추가
행 삭제
저장
저장 전 검증
```

| ID | 요구사항 | 우선순위 |
|---|---|---|
| MST-01 | **사용자 등록**: 사번, 이름, 부서, 조/팀, 직급, 권한, 재직여부를 그리드로 등록·수정·조회한다. | 필수 |
| MST-02 | **부서 등록**: 부서코드, 부서명, 사용여부를 그리드로 등록·수정·조회한다. | 필수 |
| MST-03 | **조/팀 등록**: 소속 부서, 조/팀 코드, 조/팀명, 사용여부를 그리드로 등록·수정·조회한다. | 필수 |
| MST-04 | **근무형태 등록**: 코드, 명칭, 기본분류, 시작/종료시간, 표시 색상, 실근무 여부, 특근/수당 구분 여부, 정렬순서를 그리드로 등록·수정·조회한다. | 필수 |
| MST-05 | 모든 기준정보 그리드에서 행 추가, 행 삭제, 엑셀 붙여넣기가 가능해야 한다. | 필수 |
| MST-06 | 사번, 부서코드, 조/팀코드, 근무형태코드가 중복되면 저장을 차단한다. | 필수 |
| MST-07 | 근무표에 이미 사용된 사용자, 부서, 조/팀, 근무형태는 물리 삭제 대신 사용 해제 처리를 우선한다. | 권장 |

### 3.2.1 근무형태 기준

근무형태는 기본적으로 단순한 분류를 우선 사용한다.

기본 분류:

```text
주간
야간
OFF
연차
경조사
훈련
```

실제 근무 편성 화면에서는 현장에서 바로 이해할 수 있는 단순 코드를 우선 표시한다.

예:

```text
주
야
OFF
연차
```

다만 현장 운영 및 특근수당 계산을 위해 세부 근무코드가 필요할 수 있다.

예:

```text
주-6
6주
주2
야-4
야-6
특주
특야
자녀결혼
출산휴가
```

숫자가 포함된 근무코드는 기준 근무시간에서 앞/뒤 어느 시간에 덜 근무했는지 또는 추가 근무했는지를 구분하기 위한 현장 운영 코드다.

예를 들어 08:00~20:00 기준 주간 근무에서 숫자의 위치와 값은 앞쪽 시간인지 뒤쪽 시간인지, 덜 근무했는지 더 근무했는지를 구분하는 데 사용될 수 있다.

시스템은 이러한 코드를 프로그램에 하드코딩하지 않는다.  
`work_types` 기준정보에서 등록·수정할 수 있게 한다.

근무표 저장 시 입력된 근무코드는 반드시 `work_types` 기준정보에 존재하는지 검증한다.

### 3.3 근무표 등록/수정

실제 운영 중인 월별 근무표는 가로형 구조다.

```text
직원 정보 컬럼 + 날짜별 근무 컬럼
```

등록 화면은 이 구조를 그대로 받아들이고, 저장 시 세로형 `work_schedules`로 변환한다.

| ID | 요구사항 | 우선순위 |
|---|---|---|
| SCH-01 | 월 단위 근무표를 **가로형 스프레드시트 그리드**로 등록·수정한다. 표준 입력 컬럼은 사번, 성명, 부서, 조/팀, 날짜별 근무코드다. | 필수 |
| SCH-02 | 엑셀 근무표 범위를 복사해 그리드에 다중 셀 붙여넣기 할 수 있어야 한다. | 필수 |
| SCH-03 | 그리드에서 행을 추가하거나 삭제할 수 있어야 한다. | 필수 |
| SCH-04 | 년/월, 부서, 조/팀을 선택해 저장된 근무표를 조회한다. 저장된 근무표가 없으면 해당 소속 재직자 목록 기준으로 빈 그리드를 생성한다. | 필수 |
| SCH-05 | 저장 시 가로형 그리드를 세로형 레코드로 변환하여 저장한다. 저장 단위는 사용자 × 날짜 × 근무코드다. | 필수 |
| SCH-06 | 저장 전 검증을 수행한다. 사번, 성명, 부서, 조/팀, 근무코드, 중복 근무일자를 모두 확인하고 오류가 있으면 저장을 차단한다. | 필수 |
| SCH-07 | 저장 전 미리보기를 제공한다. 신규 건수, 변경 건수, 삭제 후보 목록을 확인할 수 있어야 한다. | 필수 |
| SCH-08 | 월 데이터 저장은 upsert 방식으로 처리한다. 단, 그리드의 빈 셀 때문에 기존 근무를 자동 삭제하지 않는다. | 필수 |
| SCH-09 | 기존 근무 제거는 삭제 후보 목록에서 관리자가 명시적으로 확인·선택한 경우에만 반영한다. | 필수 |
| SCH-10 | 저장 1회를 배치로 기록하고, 셀 단위 변경은 이전 값, 이후 값, 변경자, 변경시각과 함께 이력으로 남긴다. | 필수 |
| SCH-11 | 붙여넣기 데이터는 저장 전 trim, 영문 대문자 통일, 전각 문자 처리 등 정규화를 수행한다. | 필수 |

### 3.4 근무표 저장 전 검증

근무표 저장 전 다음을 검증한다.

| ID | 검증 내용 |
|---|---|
| VAL-01 | 사번이 `users`에 존재하는지 확인한다. |
| VAL-02 | 사번이 없으면 성명으로 매칭 가능한지 확인한다. |
| VAL-03 | 성명 불일치 또는 미등록 사용자가 있으면 오류 처리한다. |
| VAL-04 | 부서가 `departments`에 존재하는지 확인한다. |
| VAL-05 | 조/팀이 `teams`에 존재하는지 확인한다. |
| VAL-06 | 근무코드가 `work_types`에 존재하는지 확인한다. |
| VAL-07 | 같은 사용자와 같은 근무일자가 중복되지 않는지 확인한다. |
| VAL-08 | 오류가 있으면 행/셀 위치와 함께 표시하고 저장을 차단한다. |

### 3.5 전체 근무표 조회

관리자와 매니저는 근무표를 조회할 수 있다.

| ID | 요구사항 | 우선순위 |
|---|---|---|
| VIEWA-01 | 전체 근무표를 월, 부서, 조/팀, 사용자, 근무형태로 필터하여 조회한다. | 필수 |
| VIEWA-02 | 엑셀형 월간 그리드로 표시하고, 근무형태별 색상으로 셀을 구분한다. | 필수 |
| VIEWA-03 | 사용자별 근무형태 집계를 하단에 표시한다. 예: 주 N, 야 N, OFF N | 권장 |
| VIEWA-04 | 권한이 있는 사용자는 조회 화면에서 편집 화면으로 이동해 수정할 수 있다. | 권장 |
| VIEWA-05 | 근무표를 CSV 또는 XLSX로 다운로드할 수 있다. | 선택 |

## 4. 데이터 요구사항

### 4.2 정합성 규칙

| ID | 규칙 |
|---|---|
| DATA-01 | 1인 1일 1근무 원칙을 따른다. 같은 사용자와 같은 근무일자는 중복될 수 없다. `(user_id, work_date)` 유니크 |
| DATA-02 | 근무표의 근무형태는 `work_types`에 존재해야 한다. |
| DATA-03 | 근무표의 사용자는 `users`에 존재해야 한다. 사번을 우선 사용하고, 사번이 없으면 성명 유일 매칭을 시도한다. |
| DATA-04 | 사용자의 부서와 조/팀은 `departments`, `teams`에 존재해야 한다. |
| DATA-05 | 중요 레코드는 물리 삭제 대신 `is_active=false` 방식의 사용 해제를 우선한다. |
| DATA-06 | 주요 테이블에는 `created_at`, `updated_at`, `created_by`, `updated_by`를 가능한 한 유지한다. |
| DATA-07 | 근무표 수정은 반드시 `schedule_change_logs`에 변경 이력을 남긴다. |
| DATA-08 | 근무표는 화면에서 가로형, DB에서 세로형으로 관리한다. |
| DATA-09 | 그리드 빈 셀로 인한 기존 근무 자동 삭제를 금지한다. 삭제는 명시적 확인을 거친 경우에만 수행한다. |

## 5. 비기능 요구사항

| ID | 요구사항 |

| NFR-05 | 직원 조회 화면은 모바일 폭에서 가로 스크롤 없이 사용 가능해야 한다. |
| NFR-06 | Supabase 키는 저장소에 커밋하지 않는다. |
| NFR-07 | 동시 사용자 약 50명 수준에서 원활히 동작하는 것을 목표로 한다. |
| NFR-08 | 개인정보는 사번, 이름, 부서, 조/팀, 직급 등 업무에 필요한 최소 정보만 수집한다. |
| NFR-09 | MCP는 사용하지 않는다. 사용자가 명시적으로 요청한 경우에만 검토한다. |

## 6. 범위 제외

아래 기능은 현재 범위에서 제외한다.

- 근무표 자동 생성 또는 자동 배정 알고리즘
- 근무 교환 신청/승인 워크플로
- 푸시 알림
- 카카오톡 연동
- 급여 시스템 연동
- 근태 시스템 연동
- 네이티브 모바일 앱
- 앱스토어 배포

향후 확장 후보로만 기록한다.

## 7. 전제 조건

- 사용자는 모두 사내 구성원이며, 사번 체계가 존재한다.
- 비밀번호 없는 로그인의 보안 수준을 조직이 초기 사용 범위에서 수용한다.
- 근무형태 체계는 부서에서 정의하고 기준정보로 관리한다.
